# Phase 1 — desktop and container foundation

Status: development foundation implemented and container checks passed on 2026-10-20. Native Windows execution/packaging and interactive end-to-end project-Dockerfile validation remain unverified.

## Implemented foundation

- Electron main/preload starts the Python backend, serves the exported Next.js UI, validates IPC senders and exposes only five named methods.
- The renderer has context isolation, sandboxing and no Node integration. The backend token is not exposed to it.
- Backend binds only to 127.0.0.1, uses configurable fixed port 43121 by default, authenticates requests and rejects browser-origin calls. A launch token arrives through stdin. Parent EOF shuts the backend down.
- Native project selection leads to a one-use selection ticket. A project Dockerfile requires a separate native approval dialog; rejection prevents build/start. Changed Dockerfile contents invalidate approval.
- Project identity derives from its canonical root. Docker containers persist between app sessions. Reuse checks the mount, user, capabilities, privileges, network and resource settings.
- The only project command exposed in this phase is the fixed Node/Python version check. Model calls, LangGraph execution and general file/terminal tools belong to subsequent phases.
- Default image contains Node.js 22 and Python 3.12; base-image digests are pinned in docker/default.Dockerfile.
- npm dependencies are pinned and package-lock.json was generated by installation inside Docker.

## GUI test environment

A default Docker seccomp profile blocked Chromium namespace creation. The setuid-helper setup alone did not resolve it. The successful GUI check used a separately approved temporary container with:

- --rm --init; non-root user from the development image.
- --network none, --cap-drop ALL, --security-opt no-new-privileges:true.
- --security-opt seccomp=unconfined to permit Chromium's user-namespace sandbox.
- Read-only root filesystem, project mount and node_modules volume; writable bounded tmpfs only at /tmp and /home/codix.
- No Docker socket or additional host directories.
- Electron's --disable-setuid-sandbox flag for this Linux container test only. The renderer sandbox stayed enabled and was asserted by the test.
- Xvfb virtual display. --init was required for proper Xvfb readiness signalling.

The ordinary project-container policy was not changed. Do not apply the GUI test's seccomp setting to project containers. The test container removed itself after completion. Missing system D-Bus and GPU services emitted stderr diagnostics, but the smoke assertions completed with exit 0.

## Reproduce the development checks

The existing development container is named codix-development. Its repository mount is /workspace. Named volumes codix-node-modules and codix-next-build hold dependencies and build cache on D:.

Run the command-check rows above through Docker. Do not run npm, Python tests, builds or Electron directly in the Windows host shell.

For the GUI test, create the temporary container with the restrictions listed above and execute npm run test:desktop. Merely running that script in the ordinary development container does not bypass its namespace restrictions.

Configuration:
- CODIX_API_PORT: integer 1024–65535, default 43121. A conflict stops startup.
- OPENAI_API_KEY: reserved for later model phases; not used by phase 1.
- Windows development expects runtime/backend/codix-backend.exe; packaged mode expects resources/backend/codix-backend.exe. There is no host-Python fallback.
- Linux container development launches python3 -m backend.server.

## Skipped checks and remaining limitations

- Native Windows desktop execution and portable packaging have not been tested or built. The approved Windows container build route for the PyInstaller artifact is still unresolved, as recorded in phase 0.
- Folder-selection cancellation was automated using a dialog stub; manual native folder-picker interaction and the full Windows GUI → Docker project workflow have not been exercised.
- Approval denial/change detection and reuse orchestration passed backend tests; actual custom project-Dockerfile build/approval through the GUI was not exercised. The real default project container and its isolation settings were checked separately.
- The GUI test intentionally has no Docker access; its prerequisite-error check is not a full successful project-prepare GUI test.
- Dockerfile approval binds the Dockerfile hash, not an immutable snapshot of the complete build context. Resolve concurrent context modification before supporting untrusted concurrent edits.
- General path-safe file operations and command policy remain phase 2 and are not exposed in this phase.
- No model API calls, token charges or model-task completion claims occurred.
- Development container and persistent project-test container remain available for reuse; the temporary GUI-check container was removed automatically.
